# Embedded account support: extension state inside consumer accounts

An extension's module marker can relocate the extension's config state into an existing consumer account at a byte offset instead of a dedicated PDA: `#[<marker>(<role> = <account>, offset = N)]`. For admin-authority that reads `#[admin_authority(admin_config = prog_config, offset = 32)]`, the 32-byte admin slot lives at bytes `[32..64)` of `prog_config`'s data. The kwargs follow the established role contract, key is the role name, value is the consumer's account name. The declaration is program-wide and rewrites the role's inject entry: the role injects the named consumer account, with the canonical constraint copied from the consumer's account-creating declaration minus `init` and `mut`, instead of the dedicated PDA param. Gated instructions that declare the embedding account use it via skip-if-declared, ones that do not get it injected PDA-verified. The rewrite is per-role, not per-spec: every other inject account keeps injecting as before. A bare marker keeps dedicated mode unchanged. Internally dedicated mode is the degenerate case `offset = 0`, one code path for both modes. Embedded mode removes one account from every gated transaction.

## Born initialized, no init instruction

In embedded mode the extension emits no initializer instruction. The consumer marks their account-creating instruction with `#[admin_initialize]` and the framework injects the bootstrap: a self-election `bootstrap_at` call appended after the consumer's writes and before the accounts move into the output, with the signer resolved through the same inject and skip-if-declared path as gate callers. This is what keeps a terminal renounce sound: the slot is provably non-zero from the moment the account exists, so an all-zeros slot unambiguously means Renounced. NotInitialized keeps its meaning from dedicated mode, empty account data, the embedding account does not exist yet. Reinit rejection rides the consumer account's own `#[account(init)]`, and the init-side front-running window does not exist in embedded mode.

The attribute rule is an iff, name-scoped and function-local. The attribute's named param must carry `#[account(init)]` in that same instruction, because `init` is the framework's only fresh-account guarantee and a bootstrap against an existing account would be an admin takeover, not an initialization. In the other direction, every instruction that declares `init` on the param bound by the marker's role kwarg must carry the attribute, so a program cannot create the embedding account without installing an admin. Shipping a program that was born renounced is a compile error, not a runtime surprise. Dedicated mode keeps the contributed `admin_initialize` instruction, and the attribute outside embedded mode is a compile error. freeze-authority does not adopt the attribute, its slot is born vacant by design and the admin appoints the first holder.

Rejected: a discriminator byte in the slot (uninit, active, renounced). It solves the same ambiguity but diverges from dedicated mode's bare 32-byte layout and charges every consumer a layout change when switching modes. Rejected: a reserved sentinel in `AdminConfig::default()` to distinguish never-bootstrapped from renounced at runtime, compile-time enforcement makes the accidental case unrepresentable and a runtime discriminant only decorates the failure it no longer prevents. Rejected: matching the embedding account by seed identity across instructions, seed specs are not unique within a program and the kwarg contract is by name, so all resolution is by the bound name in each function's own scope. Rejected: static dataflow analysis of instruction bodies, a token-level heuristic would lie on renamed imports and helper functions. Rejected: forbidding renounce in embedded mode, which amputates the API instead of answering the question.

## Management instructions keep working

An extension's discovered management instructions must work in embedded mode. The machinery is library-agnostic framework work, not extension-specific codegen, and any extension opts in the same way.

- **Role substitution on discovered fns.** The marker kwarg makes the framework replace the discovered fn's role param with the consumer's account, name and constraint. The constraint is copied from the consumer's canonical declaration, the account-creating instruction's `#[account(init, pda = ...)]`. Conflicting declarations across instructions are a compile error naming both sites. Substitution only touches fns of extensions that opt in via `bound_args`.
- **Marker-bound const args.** Extension metadata (`[[package.metadata.spel.bound_args]]` with `arg`, `from`, `default`) declares a trailing fn param bound to a module-marker kwarg. The framework appends the literal at every dispatch call site and excludes it from the IDL. The offset is never a caller-supplied instruction arg, that would be a caller-controlled write location. The IDL is client-side paperwork the program never consults, and changing the baked literal means changing the bytecode, which on LEZ is a different program_id entirely.

Rejected: emitting no management instructions in embedded mode and having the consumer hand-write them. Smaller surface, but it forks the instruction set between modes, and every adopting extension would inherit the same fork.

## Windowed primitives live on `AuthoritySlot`

Reads slice `data[offset..offset+32]`, writes splice exactly those bytes and leave surrounding consumer data untouched, too-short data is a loud `SlotOutOfBounds` error. The primitive knows nothing about states: the config type on top runs today's empty-data check first, so empty data stays NotInitialized and `SlotOutOfBounds` only ever means non-empty data whose layout disagrees with the declared offset. These primitives (`read_at`, `write_at`) live in spel-authority so every adopting library shares one implementation of the most dangerous code in the feature. The primitive stays slot-only, each config type owns adjacent bytes such as a frozen flag. The consumer embeds the extension's config type as a real field (`AdminConfig`, later `FreezeConfig`), borsh-identical to the underlying slot plus the config's own bytes, so the `authority` crate stays invisible to consumers. Only fixed-size fields may precede it, a dynamic prefix would make the offset undecidable.

Rejected: whole-data writes against the embedding account, which would overwrite the consumer's neighboring fields.

## The offset is derived on the struct

The consumer marks the slot field with `#[admin_slot]` and the `account_type` derive emits `ADMIN_SLOT_OFFSET`, a const computed as a sum of `FixedBorshSize::SIZE` terms for the preceding fields. rustc resolves aliases and evaluates the number, the macro never does token arithmetic. A preceding field whose type does not implement `FixedBorshSize` fails to compile, which turns the fixed-size-prefix rule above from documentation into an error. The derive also emits an assertion test into the consumer crate: it serializes an instance with a probe value in the slot field and asserts the probe sits at the derived offset, which pins the size arithmetic to real serialization.

The marker still takes a literal, and `lez_program` closes the gap between the two: for every embedded marker it emits a const equality assert between the marker's offset and the struct's derived const, so a struct edit the marker did not follow is a compile error naming both sides. The struct is found by its slot attribute in the consumer's own code, the entry file including manifest-declared bin paths, its inline and file-backed modules, and local path-dependency crates. Git and registry dependencies never participate, a foreign crate must not satisfy or steal the binding. When embedded markers are declared and the module's source cannot be located, compilation is refused rather than the checks silently skipped, the same rule the discovery failure tier follows. Teaching the marker to accept the const's path directly, removing the last literal, is the recorded follow-up.

## Marker is the only writer of location kwargs

In embedded mode a consumer-written location kwarg (the role name or `offset`) on the extension's gate attr is a compile error, it could only contradict the program-wide declaration. The framework's own gate stamping is the sole source of those kwargs. Per-instruction recognition of the embedding account is by seed spec, not by name: an instruction that declares the same constraint under any name reuses it via the role remap, and a param that reuses the marker's name with a different pda constraint is a compile error naming both sites. The marker's name is the lookup key for the canonical account-creating declaration, nothing more. Signer-role kwargs stay allowed, signer naming is orthogonal to slot location.

## Consequences

- The proof vehicle is a sample at a non-zero offset, including a regression test that a neighboring field survives a management write (the splice must not trample consumer data). Dedicated-mode samples' dry-run output must stay byte-identical, since dedicated mode became `offset = 0` internally.
- The wrapper-kwarg contract (wrapper args are inject-account names) gains one non-role kwarg, `offset`, and needs a one-line amendment.
- Expansion ordering is load-bearing: the injection pass runs on the consumer-authored gate attr, then the framework stamps the location kwargs. Consumer-authored args disable injection per the existing rule, framework-stamped args do not. Stamping before injecting would make every embedded gate look manual and silently stop signer injection.
- admin-authority is the first adopter. freeze-authority adopts both mechanisms for its own config and instructions. The authority-suite libraries move in lockstep, so no cross-version combination ships.
